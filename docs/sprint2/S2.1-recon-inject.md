# S2.1 — `econ-recon-inject` push-based recon bundle injection

## What it does

`econ-recon-inject` is a plugin that fires on every `context.assemble.before`
turn, queries an in-process code graph for the user's task phrase, and injects
a compact **recon bundle** (top entities + references + anchored notes) as a
context message immediately before the conversation history.

The model starts each turn with graph-derived context pre-loaded — no
`search_code` / `file_read` fan-out required.

---

## Injection position (cache-friendly)

```
[ system prompt(s) ]       ← stable, cacheable
[ recon bundle ]           ← injected here, stable position
[ conversation history ]   ← changes each turn
```

The bundle is placed **before** the conversation history so the
`[system prompt] + [recon bundle]` prefix is invariant across turns and can be
prompt-cached by the provider (Anthropic cache_read, OpenRouter caching).

The injection uses `role: "user"` so it is clearly separated from the system
block and readable by all models that support multi-turn context.

---

## Bundle format

```
=== RECON: <task phrase> ===
ENTITIES:
  <name> (<kind>) <filePath>:<lineStart>  [domain=<d> role=<r>]
    sig: <signature>
REFERENCES:
  <fromEntity> → <toEntity> (<kind>)
NOTES:
  <anchored note>
=== END RECON ===
```

- **ENTITIES** — up to 8 entities ranked by name-match relevance to the task.
  Each line includes file location and optional `@sem` domain/role tags.
- **REFERENCES** — up to 12 unique caller/callee edges among the matched entities.
- **NOTES** — prose notes anchored to matched files (populated when unerr brain
  sidecar is connected; empty from the local BunSqliteGraph stub).

---

## No-read-fan-out claim

Without this plugin a model handling a code-editing turn must:
1. `search_code(task)` — find relevant entities
2. `file_read(entity)` × N — read each entity body
3. `get_references(entity)` × N — find callers

That is 1 + 2N tool calls before the first substantive output.

With the recon bundle pre-loaded, the model sees entity names, file locations,
signatures, and caller edges in its starting context. For the common case
(routing, impact assessment, single-function edits), **zero additional reads
are needed**. Deep dives (full function bodies, secondary callers) still require
a targeted read but are rare.

### Graph singleton

The plugin maintains a lazy `BunSqliteGraph` singleton (identical to the
pattern in `packages/opencode/src/tool/graph-tools.ts`):

```js
let _graph = null
async function getGraph() {
  if (_graph) return _graph
  const { BunSqliteGraph } = await import("../../packages/code-intelligence/src/index.ts")
  const root = process.cwd()
  _graph = new BunSqliteGraph(":memory:", root)
  _graph.index(root).catch(() => {})  // background, fire-and-forget
  return _graph
}
```

The graph is indexed from `process.cwd()` on first use. The first turn of a
session may see an empty bundle (index not yet complete); subsequent turns see
the full graph.

### Task-phrase extraction

The hook `input.message` is a `UserMessage` (session metadata, no raw text).
The plugin derives the task phrase in priority order:

1. `message.text` — populated by some host integrations (v2 `SessionMessageUser`)
2. `message.summary.title` — set after compaction summarises the conversation
3. `message.summary.body` (truncated to 120 chars)
4. Fallback: `"code"` (broad enough to return common entities)

## Design constraints

- **Read-only graph access.** The plugin never writes to the graph or the
  `packages/code-intelligence` source — as required by the task boundary.
- **Graceful degradation.** If the graph fails to initialise or `recon()` throws,
  the hook logs the error and returns without injecting, so the turn proceeds normally.
- **Empty bundle skip.** When `recon()` returns zero entities and zero notes,
  no message is pushed (avoids a useless filler turn in the history).
- **isWorkflow / isOpenaiOauth paths.** In these paths `contextInject.messages`
  is not prepended to the final array (see `request.ts` line 119–132). The
  bundle is still queried and formatted (wasted work), but it is harmless; a
  future optimisation can check `input.provider` and short-circuit early.

## Test coverage

`packages/opencode/test/session/recon-inject.test.ts` — 4 tests:

| Test | Assertion |
|---|---|
| bundle before history | Injected message index < conversation-history index |
| graph-derived content | Bundle contains entity name (`parseTask`) + kind (`function`) |
| empty graph → no injection | No `=== RECON:` block when graph has no indexed entities |
| multiple entities listed | At least one `(function)` entity line in ENTITIES section |

All tests use a seeded in-memory `BunSqliteGraph` and `LLMRequestPrep.prepare()`
with a mock plugin — no live model call.
