# S2.0 — `context.assemble.before` plugin hook

## Hook signature

Defined in `packages/plugin/src/index.ts` inside the `Hooks` interface:

```typescript
"context.assemble.before"?: (
  input: {
    sessionID: string
    agent: string
    model: Model           // from @opencode-ai/sdk
    provider: ProviderContext
    message: UserMessage   // the triggering user turn
  },
  output: {
    /** Push strings to append to the assembled system prompt */
    system: string[]
    /**
     * Push plain-text model messages to inject immediately before the
     * conversation history. Use "system" for context blocks,
     * "user" for memory/recon turn-level injections.
     */
    messages: Array<{ role: "system" | "user" | "assistant"; content: string }>
  },
) => Promise<void>
```

`output.system` is the live system array (same reference used by
`experimental.chat.system.transform`); pushing to it extends the system prompt.
`output.messages` starts empty; entries are prepended before the conversation
history in the final `ModelMessage[]` sent to the LLM.

---

## Exact fire point

**File:** `packages/opencode/src/session/llm/request.ts`
**Function:** `LLMRequestPrep.prepare` (exported as `LLMRequestPrep.prepare`)

The hook fires **after** `experimental.chat.system.transform` has run (system
is fully assembled) and **before** the `messages` local variable is built (the
array that is shipped to the AI SDK). This is the latest possible point where
both `system` and `messages` can still be mutated before the model call.

Sequence within `prepare()`:

```
1. system[] assembled from agent.prompt + input.system + user.system
2. plugin.trigger("experimental.chat.system.transform", ...)   ← existing
3. plugin.trigger("context.assemble.before", ...)              ← NEW (S2.0)
4. messages[] = [...system as ModelMessages, ...contextInject.messages, ...input.messages]
5. plugin.trigger("chat.params", ...)
6. plugin.trigger("chat.headers", ...)
7. return { system, messages, tools, params, headers }
```

Approximate line in the file after the S2.0 edit: **~79–97** (after the
`experimental.chat.system.transform` block, before `const variant = ...`).

## How S2.1 and S2.4 use this hook

### S2.1 — Memory injection

A plugin (or internal service) registered for this hook:

1. Receives `input.sessionID` + `input.model` + `input.message` (the user turn).
2. Queries a memory store (e.g. unerr notes, SQLite vector index) for relevant
   memories scoped to this session/project.
3. Pushes a formatted `{ role: "user", content: "[Memory]\n..." }` entry into
   `output.messages`.

Result: the model sees the memory block immediately before the current
conversation, with no database round-trip at assembly time (fetch is done
inside the hook).

### S2.4 — Recon/call-graph injection

A plugin registered here:

1. Receives `input.sessionID` + `input.message.text` (the user's request).
2. Issues a `search_code` or `get_references` call against the unerr brain
   sidecar (UDS channel).
3. Formats the recon bundle as a system string and pushes it to `output.system`
   **or** as a user message into `output.messages` depending on provider
   preference (Anthropic prefers system; OpenAI accepts user turns).

Result: the model sees the live call-graph context without the user ever asking
for it — pure push-based injection.

## Design constraints

- **Text-only injections.** `output.messages` accepts `{ role, content: string }`.
  Multi-part or file-based injections must go through
  `experimental.chat.messages.transform` at the `WithParts[]` level (fires
  earlier in `prompt.ts`).
- **No model call.** The hook fires synchronously within the Effect runtime;
  awaited Promises are fine, but the hook must resolve before the LLM stream
  starts.
- **isWorkflow / isOpenaiOauth bypass.** When `isWorkflow` or `isOpenaiOauth`
  is true, `messages` is passed through unchanged (OpenAI OAuth and GitLab
  Workflow models manage their own context). Injections from
  `context.assemble.before` are still pushed to `output.messages` but not
  prepended in those paths. S2.1/S2.4 plugins should check `input.provider`
  and skip injection for those providers if needed.
