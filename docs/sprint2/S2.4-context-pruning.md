# S2.4 — Context-Window Pruning

**Module:** `packages/code-intelligence/src/prune.ts`
**Sprint:** Sprint 2 (context engineering layer)
**Owner:** S2.4 task

---

## What it does

`pruneWindow(messages, { tokenBudget, keepLastN })` takes an ordered
conversation window (oldest-first `Message[]`) and returns a pruned list plus
a structured `PruneReport`. The window is guaranteed to fit within `tokenBudget`
estimated tokens after pruning. The most recent `keepLastN` messages are always
returned verbatim — they are never subject to any pruning stage.

---

## Prune policy

Pruning is applied in three ordered stages. Each stage runs only if the window
is still over budget after the previous stage.

### Stage 1 — Deduplicate completed tool outputs

**Stale:** An earlier completed call to the same tool with the exact same
serialised input (JSON).

**Load-bearing:** The most recent completed result for each `(tool, input)` key.

Implementation: walk the old-message region to find the highest-index occurrence
of each `(tool, input)` key, then drop all earlier occurrences of that key.
This catches repeated `read_file` calls on the same path, repeated `shell`
invocations with the same command, etc.

### Stage 2 — Drop reasoning parts from the old region

**Stale:** `reasoning`-type parts (chain-of-thought, extended thinking output)
in messages outside the protected tail. These were useful during the turn that
produced them but rarely need to be replayed verbatim to the model.

**Load-bearing:** All `reasoning` parts inside the `keepLastN` tail (untouched).

### Stage 3 — Drop entire old assistant messages (oldest first)

**Stale:** The oldest assistant messages that no longer carry load-bearing tool
outputs (after Stage 1 deduplication) or reasoning (after Stage 2).

**Load-bearing:** User messages are *never* dropped — they are the structural
anchor of the conversation. Only `role: "assistant"` messages in the old region
are candidates for wholesale removal.

Oldest messages are evicted first so that the most recently integrated context
survives as long as possible.

---

## What is considered stale vs load-bearing

| Content | Stale when… | Always kept |
|---|---|---|
| Tool output (`type: "tool"`, `status: "completed"`) | A later call used the same tool + input | Latest result for each (tool, input) pair |
| Reasoning (`type: "reasoning"`) | Outside the `keepLastN` tail | Inside `keepLastN` |
| Text (`type: "text"`) | Entire assistant message is dropped (Stage 3) | Inside `keepLastN`; user messages never |
| User messages | Never stale | Always |
| Pending/running tool calls | Never subject to Stage 1 dedup (state not `completed`) | Structural role in the turn |

## Token estimation

The module tries to import `estimateTokens` from `./trim` (sibling S2.2). If
that module is absent (not yet landed), it falls back to `Math.ceil(chars / 4)`,
which is accurate to ±15 % for typical LLM payloads and sufficient for budget
gating.

---

## How it wires to the S2.0 hook

> **Note:** Wiring is owned by the S2.0 sibling task. This section describes
> the intended integration point only.

The S2.0 runner (or its pre-send hook) will call `pruneWindow` immediately
before serialising the message list for the model API:

```typescript
// Conceptual wiring — NOT in this module
import { pruneWindow } from "@opencode-ai/code-intelligence/prune"

const { messages: pruned, report } = pruneWindow(history, {
  tokenBudget: modelContextLimit * 0.85, // leave headroom for the response
  keepLastN: 6,
})
// log report.droppedToolOutputs, report.estimatedOutputTokens → unerr telemetry
sendToModel(pruned)
```

The `PruneReport` is surfaced to unerr telemetry so savings from context
compression appear in the savings receipt alongside model-routing savings.

## Test coverage

`packages/code-intelligence/test/prune.test.ts` covers:

- No-op when already under budget (same reference returned)
- Stays within `tokenBudget` after pruning a 50-message window
- `keepLastN` tail is always preserved verbatim
- Stale duplicate tool outputs are dropped; latest survives
- Distinct tool calls (different inputs) are not deduplicated
- Reasoning parts are dropped before whole messages
- User messages are never dropped
- Report fields (`inputMessages`, `estimatedInputTokens`, `estimatedOutputTokens`) are correct
