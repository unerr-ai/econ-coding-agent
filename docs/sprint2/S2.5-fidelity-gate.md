# S2.5 — Fidelity Gate

**Status:** implemented  
**File:** `packages/code-intelligence/src/fidelity.ts`  
**Tests:** `packages/code-intelligence/test/fidelity.test.ts`

---

## Purpose

Every compression pass in the stack (output trimming, BM25 passage selection,
context pruning) trades token cost for information loss. The fidelity gate is
a standing check: before accepting a compressed result, verify that every
"answer key" — a substring the downstream model must see — survived. If any
key is missing, the gate rejects the saving and returns the original, uncompressed
content (degrade-safe). This is the ARCH §5 guard.

---

## Verdict shape

```ts
interface FidelityVerdict {
  kept: boolean        // false if any required key is missing
  tokensSaved: number  // estimated tokens saved (can be negative)
  fidelityScore: number // fraction of keys that survived (0–1)
  missing: string[]    // keys not found in the compressed output
}
```

`assessFidelity({ before, after, answerKey })` is pure — no I/O, no mutation.

---

## Gate wrapper

```ts
gateCompression(compressor, input, answerKeys, opts?)
// → { output, verdict, degraded }
```

`output` is the compressed result when all keys survive (`degraded: false`), or
the original `input` when any key is missing (`degraded: true`). The `verdict` is
always reported so callers can observe token savings and missing keys.

For non-string compressors (BM25 passage arrays, message arrays) supply
`opts.serializeBefore` and `opts.serializeAfter` to project both sides to
strings before key-checking.

---

## Regression set

Four compressor types are tested in `fidelity.test.ts`:

| Compressor | Case | Answer keys | Gate result |
|---|---|---|---|
| `smartTruncate` (trim.ts) | Normal budget (300 tok) | `HEAD_SENTINEL`, `TAIL_SENTINEL` | Green — both survive in head/tail |
| `smartTruncate` (trim.ts) | **Over-aggressive** (50 tok) | `MIDDLE_SENTINEL` | **Red** — middle elided, gate rejects |
| `rankPassagesByPrompt` (BM25) | topK=3, relevant query | `BM25_TARGET_PHRASE` | Green — relevant passage in top-3 |
| `rankPassagesByPrompt` (BM25) | **Over-aggressive** topK=1, unrelated query | `BM25_TARGET_PHRASE` | **Red** — wrong passage returned, gate rejects |
| `pruneWindow` (prune.ts) | Recent message in keepLastN | `RECENT_FACT` | Green — recent tail never dropped |
| `pruneWindow` (prune.ts) | Stale tool outputs deduped | `PRESERVED_KEY` | Green — recent text preserved |

Two of the six cases deliberately trigger a gate rejection, proving the gate bites.

## How it plugs in as a standing gate

Any new compression step should be wrapped:

```ts
const { output, verdict } = gateCompression(myCompressor, input, requiredKeys)
if (verdict.tokensSaved > 0) {
  emitSavingsEvent({ saved: verdict.tokensSaved, fidelity: verdict.fidelityScore })
}
// `output` is always safe to use — original if fidelity failed
```

The gate is cheap (string scan + token estimate) and stateless. It must run
inside the same call frame as the compressor so the fallback is transparent
to callers. Never accept a compressed result without first running it through
`assessFidelity` with the answer keys for the current task context.

---

## What counts as an answer key

Answer keys are caller-supplied. Good sources:

- Explicit user questions: extract the key entity/fact names.
- Tool-call inputs: the file path, function name, or query string the model
  needed to see.
- Prior model output markers: if the model already named a symbol, that name
  must survive into the next window.

Vague keys (single common words) cause false positives. Prefer multi-word
phrases or structured tokens (`ERROR_CODE`, `function_name`, `file.ts:42`).
