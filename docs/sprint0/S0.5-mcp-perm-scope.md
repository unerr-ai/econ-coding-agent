# S0.5 MCP-Permission Bypass Scope

## Summary

**Verdict: GO — A minimal Z3 patch IS needed** to close a MCP tool execution permission bypass. The `tool.execute.before` governance hook is properly invoked for MCP tools in the main session path, but the underlying tool construction in `mcp/catalog.ts` lacks built-in permission gating, creating risk if that layer is accessed directly or if future code bypasses the session wrapper.

---

## Dispatch & Permission Flow

### 1. Built-in Tool Dispatch (Core Path)
**File:** `packages/core/src/tool/registry.ts:49`
- `settleWith()` function: looks up tool registration by name, calls `settle()` to execute
- **Permission gate:** Applied by the calling layer (session or consumer)

### 2. MCP Tool Definition & Creation (Catalog Layer)
**File:** `packages/opencode/src/mcp/catalog.ts:42-81`
- `convertTool(mcpTool, client, timeout)` function:
  - Creates "ai" library tool definitions from MCP server tool specs
  - **Line 54: Direct MCP client call** — `await client.callTool(...)`
  - **NO plugin trigger wrapper at this layer** — permission check omitted
  - Returns tool with execute function ready to use

### 3. MCP Tools Registration (MCP Service)
**File:** `packages/opencode/src/mcp/index.ts:628-651`
- `MCP.Service.tools()` method:
  - Calls `convertTool()` for each connected MCP server tool
  - Returns `Record<string, Tool>` of unwrapped tools

### 4. Session Tool Resolution (Permission Gate)
**File:** `packages/opencode/src/session/tools.ts:298-393`
- `SessionTools.resolve()` method:
  - **Line 298:** Fetches MCP tools via `mcp.tools()`
  - **Lines 309-313:** Wraps each tool's execute with `plugin.trigger("tool.execute.before", ...)`
  - **Lines 327-331:** Wraps result with `plugin.trigger("tool.execute.after", ...)`
  - Also applies permission check at line 315: `ctx.ask({ permission: key, ... })`

## Key Finding: Permission Gate Coverage

### Does the `tool.execute.before` hook intercept MCP tool calls?

**YES** — in the main codepath:
- MCP tools ARE wrapped with the plugin hook in `SessionTools.resolve()` (lines 309-327)
- Permission check IS called at line 315

**BUT there is a structure risk:**
- The `convertTool()` function in `catalog.ts` has NO built-in permission gating
- If MCP tools are accessed outside the session wrapper (e.g., direct `mcp.tools()` usage, testing frameworks, future refactoring), they bypass the governance gate
- The hook depends on the **session layer** to wrap tools — not on the tool definition itself

---

## Why This Matters for econ's Governance Gate

econ's in-loop governance (S6.3) must fire **before** ANY tool execution. The current design:

1. ✅ Built-in tools have governance applied at multiple layers (session wrapper + registry lookups)
2. ✅ MCP tools have governance applied at the session wrapper layer
3. ⚠️ **Structural gap:** MCP tool definitions (`convertTool()`) trust the caller to apply permission gating — no fail-safe

If a future code path calls `mcp.tools()` results directly, or if `convertTool()` is reused in a new context (e.g., CLI, testing, plugin delivery), the governance gate is silently bypassed.

---

## GO: Minimal Z3 Patch Recommendation

### Patch Scope

Move permission gating **into** the `convertTool()` function itself, making it a property of the tool definition, not the caller.

### Files to Patch

**1. `packages/opencode/src/mcp/catalog.ts` (lines 42-81)**

```typescript
export function convertTool(
  mcpTool: MCPToolDef,
  client: Client,
  timeout?: number,
  onBeforeExecute?: (toolName: string) => Promise<void>, // NEW: optional permission hook
): Tool {
  const inputSchema: JSONSchema7 = { /* ... */ }

  return dynamicTool({
    description: mcpTool.description ?? "",
    inputSchema: jsonSchema(inputSchema),
    execute: async (args: unknown, options) => {
      // NEW: Call permission hook before execution (if provided)
      if (onBeforeExecute) {
        await onBeforeExecute(mcpTool.name)
      }

      const result = await client.callTool(
        { name: mcpTool.name, arguments: (args || {}) as Record<string, unknown> },
        CallToolResultSchema,
        { /* ... */ }
      )
      // ... rest of execute logic
    },
  })
}
```

**2. `packages/opencode/src/mcp/index.ts` (lines 646-648)**

Pass the governance callback into `convertTool()`:

```typescript
// Line 646-648 context: within the tools() Effect
```

If decoupling governance from session layer is desired, update the wrapper to pass the permission callback:

### Impact

- **Fail-safe:** Governance is now a property of MCP tool definitions, not caller responsibility
- **Backward compatible:** The hook parameter is optional; existing callers work unchanged
- **Surface code paths:** Any future code using `mcp.tools()` or `convertTool()` will have governance by default
- **Testing:** Test fixtures that use MCP tools directly will correctly fail if permission is not provided

---

## Alternative: No Patch (Current State)

If the team determines that the session layer is sufficient (all real usage goes through `SessionTools.resolve()`):

- **Risk acceptance:** Relies on social contract — future developers must remember to wrap MCP tools
- **Cost:** Slightly simpler codebase, lower cognitive load for new contributors
- **Tradeoff:** Loses fail-safe property; governance gap becomes a landmine

---

## Patch Effort Estimate

- **Lines changed:** ~15 (add optional parameter, call hook, update callers)
- **Risk level:** Low — additive change, backward compatible
- **Test burden:** Add 1–2 test cases verifying hook is called when provided
- **Timeline:** ~30 min implementation + review

---

## Recommendation for S6.3 (In-Loop Governance Gate)

**GO — Implement the patch.** It costs minimal effort now and prevents governance bypass scenarios in later phases (plugin delivery, CLI, testing frameworks). The fail-safe property is worth the ~15 line change.

If the patch is not done, document the **assumption** that all MCP tool execution happens via `SessionTools.resolve()` and add a lint rule to flag direct calls to `mcp.tools()` in main code (not tests).
