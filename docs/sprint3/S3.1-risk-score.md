# S3.1 — Code-Structural Risk Score

**Module:** `packages/code-intelligence/src/risk.ts`  
**Sprint:** 3 (the moat)  
**Status:** shipped

---

## What it is

A 0–100 code-structural risk score computed inline from the bun:sqlite call graph.
The score is **purely structural** — no prompt-text classification, no heuristics about
task type. It answers: "how dangerous is it to edit this entity right now?"

---

## Factors and weights

| Factor | Raw value | Ceiling | Weight |
|---|---|---|---|
| `fanIn` | Direct caller count (edges where `to_entity = name`) | 15 callers | **35%** |
| `blastRadius` | Unique caller-file count reachable transitively via BFS (depth ≤ 5) | 30 files | **35%** |
| `centrality` | Connectivity proxy: `fanIn + fanOut` | 20 | **20%** |
| `cx` | Body complexity proxy: `lineEnd − lineStart` (line count) | 100 lines | **10%** |

Each factor is normalized to `[0, 1]` against its ceiling (clamped, not scaled beyond 1), then the
weighted sum is multiplied by 100 and rounded to an integer.

```
score = round(
  0.35 * min(fanIn / 15, 1)
+ 0.35 * min(blastRadius / 30, 1)
+ 0.20 * min(centrality / 20, 1)
+ 0.10 * min(cx / 100, 1)
) * 100
```

### Why these weights

`fanIn` and `blastRadius` share 70% because direct and transitive dependents are the clearest
break-risk signal — editing a function with 10 callers is concretely riskier than editing an
isolated leaf. `centrality` at 20% captures hub status (a highly connected entity is expensive to
reason about even if callers are few). `cx` at 10% is a small tiebreaker: large, complex bodies
have more surface area for mistakes.

---

## Blast-radius BFS

`blastRadius` is computed by a file-level BFS over the caller graph:

1. Start: the entity's own file is marked visited; the entity name is the initial frontier.
2. Each BFS level: for each name in the frontier, call `getCallers(name)` → collect
   `ref.fromFile` values not yet visited → mark them visited → fetch their entities via
   `getEntitiesInFile(fromFile)` → their names become the next frontier.
3. Stop at depth 5 or when the frontier is empty.
4. Return `visitedFiles.size - 1` (excluding the entity's own file).

This is O(depth × frontier × edges) and stays bounded by the depth cap.

---

## unerr-cli lift

The approach is derived from two unerr-cli modules:

- **`src/intelligence/edit-impact.ts`** (`computeEditImpact`, `EditImpactGraph`) — the pattern of
  a narrow async graph interface + BFS caller traversal + configurable thresholds.
- **`src/intelligence/health-grade.ts`** (`computeScore`) — the weighted multi-factor scoring
  pattern with explicit ceilings and linear normalization.

Key adaptation: unerr-cli uses CozoDB (Datalog) for graph queries; here we use the bun:sqlite
graph surface (`RiskGraph` interface) and implement BFS in TypeScript rather than Datalog.

## API

```typescript
// Single entity
computeRisk(graph: RiskGraph, target: Entity): Promise<RiskResult>
// → { score: 0–100, factors: { blastRadius, fanIn, centrality, cx } }

// Turn-level aggregation (S3.2 consumption point)
computeTurnRisk(graph: RiskGraph, entities: Entity[]): Promise<TurnRiskResult | null>
// → { score, topEntity, perEntity[] } | null
```

### RiskGraph interface

```typescript
interface RiskGraph {
  getEntity(key: string): Promise<Entity | null>
  getCallers(entityKey: string): Promise<Reference[]>
  getReferences(entityKey: string): Promise<Reference[]>
  getEntitiesInFile(filePath: string): Promise<Entity[]>
}
```

`BunSqliteGraph` satisfies `RiskGraph` structurally (all four methods are implemented, including
the new `getEntitiesInFile`).

---

## BunSqliteGraph integration

`BunSqliteGraph.riskScore(filePath)` delegates to `computeRisk`:

1. Calls `getEntitiesInFile(filePath)` to get all entities in the file.
2. Calls `computeRisk(this, entity)` for each entity.
3. Returns `max(scores) / 100` — normalized to `[0, 1]` to maintain the existing
   `CodeIntelligence.riskScore` signature.

---

## How S3.2 consumes computeTurnRisk

S3.2 (the router) calls `computeTurnRisk` at the start of each routing decision, passing the
entities touched by the current turn (derived from the turn's edit targets):

```typescript
const turnRisk = await computeTurnRisk(graph, entitiesInTurn)
if (turnRisk && turnRisk.score >= ESCALATION_THRESHOLD) {
  // Route to stronger model
  return routeToSenior(turn, { reason: "structural-risk", score: turnRisk.score, topEntity: turnRisk.topEntity })
}
```

Suggested threshold: `60` (empirically: entities with 9+ callers and moderate body size reach this
level; pure leaves with no callers score 0–5).

The `perEntity` breakdown lets the router log which specific entity drove escalation, supporting
the hysteresis and double-pay accounting described in the architecture decision.
