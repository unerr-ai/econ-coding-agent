# S4.4 — Batch-Then-Fan-Out Orchestration Rule

**Module:** `packages/code-intelligence/src/fanout.ts`  
**Sprint:** 4 (orchestration discipline)  
**Status:** shipped

---

## What it is

A **discipline rule** that encodes how the orchestrator (and delegated specialists)
dispatch work: batch independent work into ONE MESSAGE and let OpenCode run it
concurrently. NEVER loop the main thread file-by-file over mechanical work — that is
waste. Instead, partition calls into waves (S4.2) and fan each wave out at once.

This rule applies to both the main conductor and every specialist (executor, worker,
oracle).

---

## The rule, as code

From packages/code-intelligence/src/fanout.ts:

```typescript
export const BATCH_THEN_FANOUT_RULE =
  "Batch independent work into one wave and dispatch it in a single message so the " +
  "calls run concurrently. NEVER loop the main thread file-by-file over mechanical " +
  "work — partition the calls into waves and fan each wave out at once."
```

This is a **constant**, not just documentation — it can be cited in:

- **Prompts:** Inject the rule into the system prompt of the conductor/executor so they
  know the expectation.
- **Logs:** Emit it when documenting why a certain parallelization strategy was chosen.
- **Tests:** Assert that the orchestrator respects the rule (no loops, one wave per
  dispatch).

---

## Why this rule matters

**Cost impact:** Looping the main thread file-by-file over mechanical work (e.g. renaming
a variable across 50 files) means:

1. 50 separate messages (token overhead from repeated context/prompt)
2. 50 separate model inferences (latency + API call overhead)
3. No parallelism — each file processed sequentially

**Batched + fanned out:** All 50 reads + 50 edits dispatched in two waves (reads then edits):

1. 2–3 messages total (only when a dependency chain requires sequential waves)
2. Read wave runs concurrently, write wave runs concurrently
3. Model sees only the refactor task once, then reasons about all paths together

**Savings model:** S4.2's `planWaves` quantifies the wave count; fewer waves = less main
thread overhead.

---

## Scope: where the rule applies

| Role | Application | Example |
|------|-------------|---------|
| Conductor | Every turn's orchestration | "These 3 recon calls are independent; dispatch in one message, not three" |
| Executor specialist | Within its delegated task | "Run all 5 linter checks in one `bash` call, not five" |
| Worker specialist | Refactor / codemod tasks | "Apply the rename to all 20 call sites in one `edit` wave" |
| Oracle specialist | Review consolidation | "Review all diffs in one pass, return one digest" |

## Encoding: `planWaves` documents the rule

The `planWaves` function (S4.2) is the **concrete encoding** of this rule in code:

```typescript
export function planWaves(calls: FanoutCall[]): FanoutCall[][]
```

It partitions calls into sequential waves such that each wave is mutually independent
and can run with `concurrency: "unbounded"`. The result is the **minimum number of
waves** — if 5 calls are all independent, they fit into 1 wave; if 2 write to the
same file, they split into 2 sequential waves.

**Using the planner to enforce the rule:**

1. **Detect the work:** Identify all intended tool calls for a task.
2. **Plan the waves:** Call `planWaves(calls)`.
3. **Dispatch per wave:** For each wave, emit one message with all calls in that wave.
4. **Never loop:** Do NOT emit one message per call (that would create N waves of 1 call each).

---

## Example: `codemod` specialist respecting the rule

**Task:** "Rename `OldFunction` to `NewFunction` across 30 files."

**Bad (looping, violates the rule):**

```
Message 1: Edit src/a.ts (OldFunction → NewFunction)
Message 2: Edit src/b.ts (OldFunction → NewFunction)
Message 3: Edit src/c.ts (OldFunction → NewFunction)
...
Message 30: Edit src/z.ts (OldFunction → NewFunction)
```

Cost: 30 messages, 30 inferences, no parallelism, token blowup.

**Good (batched + fanned, respects the rule):**

```
Message 1:
  - Edit src/a.ts (rename)
  - Edit src/b.ts (rename)
  - Edit src/c.ts (rename)
  ...
  - Edit src/z.ts (rename)
  [OpenCode runs all 30 edits concurrently via Effect.forEach unbounded]

Message 2 (if needed, e.g. import propagation):
  - Read src/main.ts
  - Read src/index.ts
  [Digest: "Renamed in 30 files, no import changes needed"]
```

Cost: 2 messages, 1 main inference, 30 concurrent edits.

## Batch-then-fan-out workflow

For any multi-site mechanical work:

1. **Collect the operations:** Read-only phases (searches, traces) → identify all sites to change.
2. **Partition into waves:** Use `planWaves` or reason manually — independent operations in one
   wave, dependent operations across sequential waves.
3. **Dispatch per wave:** Emit ONE message per wave with all calls in that wave.
4. **Integrate the digest:** The child specialist/model returns a digest (not raw transcript);
   the orchestrator chains it forward.

---

## Exceptions (rare)

The rule is not absolute when:

- **Interactive debugging:** A specialist is tracing an unknown bug and needs to read results
  before deciding the next read. (Inherently sequential.)
- **Fallback / retry:** A tool call fails; one retry needed. (Not repetitive looping.)
- **Resource limits:** A single wave is too large for one message (e.g. > 10MB args). (Batch
  by size, not by file count.)

When an exception applies, **document it** — a comment or log line explaining why the loop
is necessary. The rule is the default; exceptions are explicit.
