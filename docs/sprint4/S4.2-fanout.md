# S4.2 — Parallel Fan-Out of Independent Tool Calls

**Module:** `packages/code-intelligence/src/fanout.ts`  
**Sprint:** 4 (parallelism)  
**Status:** shipped

---

## What it is

OpenCode **already runs the tool calls of one assistant message concurrently** — we did NOT
rebuild that loop. Instead, this module adds the *planning* side: partition intended tool
calls into sequential WAVES such that every call within a wave is mutually independent and
safe to run with unbounded concurrency. Two calls conflict when they touch the same path
with at least one write (write/write or read/write).

---

## OpenCode's built-in concurrency

From packages/opencode/src/session/processor.ts (~lines 879–883):

```typescript
Effect.forEach(toolCalls, {
  concurrency: "unbounded"  // runs all calls in parallel by default
})
```

**Key fact:** OpenCode's session processor **awaits all tool calls in one message together**
with `Effect.forEach(..., { concurrency: "unbounded" })`. The `tool.execute.before` hook
(S4.1) fires **per call before dispatch**. So a model that emits N independent tool calls in
a single message **already gets one parallel wave** — concurrent execution is baked in.

Our job is NOT to rebuild the loop, but to *verify and document* the fan-out property via
`planWaves`, so the orchestrator can reason about whether a set of calls is truly
concurrent or needs sequential waves.

## Conflict detection

Two calls conflict and **must NOT share a wave** when one writes a path the other reads or
writes (write/write or read/write on the same path). Two read-only calls never conflict.

From packages/code-intelligence/src/fanout.ts:

```typescript
function callsConflict(a: FanoutCall, b: FanoutCall): boolean {
  const aw = new Set(a.writes ?? [])
  const bw = new Set(b.writes ?? [])
  if (aw.size === 0 && bw.size === 0) return false  // two reads never conflict
  const ar = a.reads ?? []
  const br = b.reads ?? []
  // a's writes vs b's reads+writes
  for (const p of aw) if (bw.has(p) || br.includes(p)) return true
  // b's writes vs a's reads
  for (const p of bw) if (ar.includes(p)) return true
  return false
}
```

## Wave planner

`planWaves` partitions a set of tool calls into the minimum number of sequential waves:

```typescript
export function planWaves(calls: FanoutCall[]): FanoutCall[][] {
  const waves: FanoutCall[][] = []
  for (const call of calls) {
    let placed = false
    for (const wave of waves) {
      if (wave.every((other) => !callsConflict(call, other))) {
        wave.push(call)
        placed = true
        break
      }
    }
    if (!placed) waves.push([call])
  }
  return waves
}
```

**Greedy first-fit algorithm:** Each call joins the earliest wave it does not conflict
with; otherwise it opens a new wave. Input order is preserved.

**Ideal case:** A fully independent set returns as a **single wave** (the common case).
The orchestrator dispatches it in one message and OpenCode runs it concurrently.

## The FanoutCall model

```typescript
export interface FanoutCall {
  id:     string      // Stable id to identify the call in the plan
  tool:   string      // Tool id (e.g. "read", "edit", "graph")
  reads?: string[]    // Paths this call reads. Default: none.
  writes?: string[]   // Paths this call writes/mutates. Default: none.
}
```

**Example:** Three independent recon calls:

```typescript
const calls = [
  { id: "c1", tool: "graph", reads: ["src/a.ts"], writes: [] },
  { id: "c2", tool: "read", reads: ["src/b.ts"], writes: [] },
  { id: "c3", tool: "grep", reads: ["src/"], writes: [] }
]
planWaves(calls)  // → [[ c1, c2, c3 ]]  one wave, all concurrent
```

**Conflicting calls separated into waves:**

```typescript
const calls = [
  { id: "e1", tool: "edit", reads: ["src/a.ts"], writes: ["src/a.ts"] },
  { id: "e2", tool: "edit", reads: ["src/a.ts"], writes: ["src/a.ts"] }
]
planWaves(calls)  // → [[ e1 ], [ e2 ]]  two waves, sequential
```

## Verification utilities

```typescript
// True when all calls are mutually independent — run as one wave
export function isSingleWave(calls: FanoutCall[]): boolean {
  return planWaves(calls).length <= 1
}

// True when a call is read-only
export function isReadOnly(call: FanoutCall): boolean {
  return (call.writes?.length ?? 0) === 0
}
```

## Integration point

The planner is currently a **pure module** — used by the orchestrator to verify and
document fan-out properties. It does NOT block or change execution; OpenCode runs the
calls concurrently regardless. This allows the orchestrator to:

1. **Reason about parallelism:** "Are these N calls concurrent or sequential?"
2. **Log the wave plan:** "Dispatched wave 1 with 3 calls, wave 2 with 1 call"
3. **Verify model behavior:** Confirm the model respects the single-wave invariant for
   independent work (S4.4 rule)
